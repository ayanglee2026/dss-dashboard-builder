# 指标库全流程（Metric Library）

> **依赖与前置**
> - 前置：`domain-mapping.md`（字段映射）、`metric-dictionary.md`（口径表模板）
> - 被依赖：`assembly-config.md`（组装时按指标库选呈现方式）
> - 覆盖阶段 2–4：指标目录 → 数据验证 → 版本化发布

指标库不是一张一次性口径表，而是一个**有版本、可查询、经数据验证**的正式产出物。真实作业流程（羊哥原话）：

```
1 确认数据范围定义 → 2 建指标目录（基础+衍生+算法+说明书）
→ 3 MVP 数据验证 → 4 发布指标库（版本号 + changelog）
```

## 第 1 步：确认数据范围及定义（阶段 1 前置）

先写《数据字段定义表》：字段清单、每字段业务含义、类型、主键/唯一 ID、单位、明细还是已聚合、来源、更新频率。**只确认「数据是什么」，不做质量检查**（质量检查在数据验证）。

## 第 2 步：建指标目录（阶段 2）

两类指标，但**基础指标不是全收录**：

- **基础指标（直接字段）**：分两类收录
  - **必进**：派生指标的依赖字段（公式要用到的基础字段，缺了公式没法表达）
  - **让用户选**：其他基础字段，逐个问「这个要不要进库/要不要展示」，别默认全塞进去——数据里有很多中间字段、校验字段，不是业务要看的指标
- **派生指标**：算出来的，逐个确定定义 + 算法。三类通用派生模式（占比率 / 净变动 / 达成率）见 `metric-dictionary.md`

**精选原则**：指标库是「业务要看的指标」，不是「数据字段清单」。先收派生指标，再收派生指标依赖的基础字段，最后让用户从剩余字段里挑要进库的。字段清单在阶段 1 的《数据字段定义表》里已经全列了，指标库不用重复全列。

产出「指标说明书」——每指标一行：

| 指标名 | 类型 | 定义/业务含义 | 公式/口径 | 来源字段 | 聚合粒度 | 单位 |
|--------|------|--------------|----------|---------|---------|------|

**公式命名约定（关键）**：指标说明书和指标库 HTML 是**给用户看的**，「公式」列必须用**用户业务名**（如「在租单元数 ÷ 总规模 × 100」），不能用英文字段名（`current_rented / total_units`）或通用字段名（`metric_part / metric_total`）。技术字段名只出现在代码里，「来源字段」列可以放技术名，但「公式」列用业务名——用户没程序员背景，看到 `current_rented` 看不懂，公式等于白写。

### 指标库 HTML 文档（可查询）

把指标说明书做成单文件 HTML，支持搜索 + 按类型/类别筛选 + 指标卡片（名称/字段/公式/口径）。结构：

```javascript
var metrics = [
  {cat:'规模', type:'base', name:'总规模', field:'total_units', formula:'Excel直接导入。入住率分母'},
  {cat:'派生', type:'derived', name:'入住率', field:'occupancy_rate', formula:'在租单元数 ÷ 总规模 × 100'},  // 公式用业务名，field 用技术名
  // ...
];
```

搜索匹配「名称 + 字段名 + 公式 + 类别」，筛选区分基础/派生。见 demo-dss 的 `metric-library.html`（49 指标完整示例）。

**此 HTML 是成品标配交付物**，随成品一起交付给间接用户查口径，成品内要有「指标说明」入口直达（见 `end-user-usability.md` 第 3 节）。

## 第 3 步：MVP 数据验证（阶段 3）

用最简方式跑通「导入→清洗→聚合→派生」链路，**核心是验证数据 + 指标算法正确，不是做界面**。五维验证：

| 维度 | 验证方法 |
|------|---------|
| 数据质量 | 缺失率、异常值（超大值>中位数×10、负值、超上限）、格式不一致、重复 key、脏值占位 |
| 数据自洽 | 交叉校验：分项之和 = 合计字段（误差容忍 0.01） |
| 聚合正确 | sum 一致性：父节点 = 子节点求和 |
| 指标算法 | 每个派生指标抽样 2–3 实体手工核算 vs 程序结果；全量合计对账 |
| 边界用例 | 空数据、除零、缺失字段、单条记录，不报错不 NaN |

产出《数据验证报告》：每项「预期 vs 实际 → 通过/失败」。**通过 = 报告全绿 + 抽样对账一致 + 异常值已处理确认**。失败项处理完才进第 4 步。详细清单见 `data-profiling.md`。

## 第 4 步：指标库发布（阶段 4）

验证通过 → 指标库「草案」转「正式版」，明确**版本号 + changelog**。changelog 记录：

- 收录内容（基础 N 个 + 派生 M 个）
- **口径修正**（数据验证发现的，记录溯源）——这是 changelog 的核心价值
- 清洗规则（随指标库一起固化）
- 待确认项（不阻塞发布，发布后跟进）

后续口径变更都走版本，**不静默改**。见 demo-dss 的 `metric-changelog.md`。

## 真实坑（经营日报案例）

1. **直接字段 vs 派生字段要分清**：Excel 里「净新签」是业务手填字段，和派生公式（换租签约+总新签−总退租−换租退租）有 141/360 处差异。结论：页面直接用字段，公式仅作旧表兜底。收录指标时，**凡 Excel 里有现成字段的，先确认是「直接字段」还是「可派生」**，别急着套公式。
2. **字段全 0 要确认**：企业退租列 360 行全 0，要问用户「本期无此业务」还是「字段已废弃」，别默认对。
3. **超大值判据会误报**：总库存「>中位数×10」判据把大楼栋正常库存误报为异常，判据须结合业务上限（详述见 `data-profiling.md` 质量层面）。
