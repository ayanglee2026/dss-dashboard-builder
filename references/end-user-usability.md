# 间接用户可用性（End-User Usability）

> **依赖与前置**
> - 前置：`assembly-config.md`（成品形态已定）、`anomaly-todo.md`（异常/待办/策略链）、`metric-library.md`（指标库 HTML）、`permission.md`（权限）
> - 被依赖：`acceptance-checklist.md`（本文第 7 节给「间接用户可用性」验收清单，供其引用）
> - 覆盖跨阶段 5-8，主要在阶段 6 视觉打磨 + 阶段 8 验收时兼顾；作为独立的交付设计维度。

## 1. 为什么单独一篇

skill 之前全程从**直接用户开发**角度写：怎么定目标、怎么建指标库、怎么组装部署。但成品做出来交付后，**间接用户——成品工具的最终使用者——在没有 agent 的情况下，怎么独立把这个工具用起来做监测/分析**，这层设计缺失。

**间接用户画像**：不懂代码、不装 Playwright、不读 skill 文档、不一定会主动求助直接用户。他们面对的是**成品工具**，不是 skill。

本篇补这层：成品要**自解释、可自主操作**。目标：成品交付后，间接用户能独立完成「看数据 → 查口径 → 收预警 → 处理待办」的闭环，不依赖直接用户或 agent 在场。

## 2. 成品内置操作指引（Onboarding）

成品首屏/帮助入口要内置操作指引，**不是外部 skill 文档**（间接用户看不到 skill）。三件套：

- ① **这是什么工具**：一句话 + 给谁用（如「本工具帮店长看各楼栋入住率和新签退租」）
- ② **怎么用**：导入 → 看数据 → 筛选 → 导出，3-5 步（用截图或图示，别只写文字）
- ③ **指标口径在哪查**：链到指标库 HTML（见第 3 节）

间接用户首次打开要有「新手引导」或明显的「使用说明」入口，别藏深。指引页结构模板：

```markdown
# <工具名>
一句话：<给谁用，解决什么问题>

## 快速上手（3 步）
1. 打开 <数据源文件>，点「导入」
2. 看 <核心指标>，用顶部筛选器看不同 <维度/时间>
3. 需要明细点「导出」

## 指标口径
点右上角「指标说明」，查每个指标怎么算的。
```

## 3. 指标说明页作为标配交付物

`metric-library.md` 已经做了「指标库 HTML 可查询」（搜索 + 按类型筛选 + 指标卡片）。**本节明确：这个 HTML 是成品标配交付物，随成品一起交付给间接用户。**

- 成品内要有「指标说明」入口**直达**这个 HTML，不是埋在文件目录里等用户自己找
- **路径规划**：指标说明页和看板页面放**同一目录**（或明确相对路径），入口链接用正确路径——「指标说明」点进去 404 是最常见的交付事故
- 每个指标卡复用 metric-library 结构：名称 / 业务含义 / 公式（业务名）/ 口径 / 来源字段
- 本节只补「作为交付物 + 成品入口」这层，不重复 HTML 实现细节

## 4. 状态/错误提示面向非技术用户

`acceptance-checklist.md` 提了「空态/错误态有提示」但太浅。标准：提示要**说清是什么问题 + 给出下一步动作**，不是报错堆栈、不是干瘪的「无数据」。

| 场景 | 非技术用户文案标准 |
|------|------------------|
| 导入坏文件 | 「文件格式不对，列 XXX 缺失，请对照模板」+ 给模板下载入口 |
| 后端挂掉 | 「数据加载失败，可能是网络问题，稍后重试；持续失败请联系 XXX」 |
| 空数据 | 「当前筛选无数据，试试放宽筛选/切换日期」不是「无数据」 |
| 权限不足 | 「此功能需 XX 权限，联系管理员 XXX」不是只隐藏按钮 |
| 导入部分失败 | 「成功 N 行，失败 M 行（详见清单），可修正后重试」 |

**标准一句话：提示 = 问题描述 + 下一步动作 +（可选）求助方式。**

## 5. 间接用户自主操作

skill 现在假设直接用户做导入/更新/导出。本节补「间接用户能自主操作」的设计：

- **导入/更新**：入口明显、导入前有模板可下载、导入后有校验摘要（导入了多少行/哪些失败）、失败可重试
- **导出**：间接用户能自己导出（HTML 快照 / Excel 明细），导出后文件能离线打开（衔接 `export-report.md`）
- **筛选/视角切换**：间接用户能自己切换看不同维度，操作简单到**不暴露技术概念**（间接用户不用懂「视角切换刷新筛选器」这种坑，那是开发侧要处理的，不是用户要理解的）

**给间接用户一张「日常操作清单」**（每天/每周做什么），让用户有节奏地用工具，而不是「想起来才点开」：

```markdown
## 日常使用
- 每天上班：打开 → 看异常预警 → 处理待办
- 每周一：导出上周明细 → 发给上级
- 数据更新后：重新导入 → 看校验摘要确认导入成功
```

## 6. 监测/待办的间接用户管理

`anomaly-todo.md` 已有规则→待办→策略链（功能层）。本节补「间接用户怎么参与」，**只管看懂和执行，不做规则编辑**（规则/阈值调整由直接用户或授权的运营做，间接用户只需理解和使用）：

- **看懂规则**：规则不能只藏在代码里。成品要有「规则说明页」（每条规则：看什么 / 阈值 / 触发什么），间接用户能理解**为什么被预警**
- **处理待办**：待办不只是「看清单」，要能标记状态（待处理/处理中/已处理），处理完能回写结果，形成闭环
- **执行策略**：策略建议要有「执行记录」入口，间接用户能记下「按这条策略做了什么」，供直接用户回溯和调规则

> 边界：本节**不设计**「间接用户自己改阈值/迭代规则」——那是运营/分析师的活，塞给看板使用者会让工具复杂化、也让 skill 跑偏成策略管理平台。规则调整由直接用户（开发侧）按 `anomaly-todo.md` 的规则文件版本化来做。

## 7. 间接用户验收清单

在 `acceptance-checklist.md` 第三层「交互可用性」后，加第四层「间接用户可用性」：

```markdown
## 第四层：间接用户可用性（成品交付前必验）
- [ ] 成品有内置操作指引，间接用户首次打开能看懂
- [ ] 指标说明页可达，间接用户能自助查口径
- [ ] 状态/错误提示是非技术用户能懂的文案（对照本文第 4 节标准）
- [ ] 导入/导出/筛选间接用户能自主操作
- [ ] 规则有说明页，间接用户能看懂为什么被预警
- [ ] 待办能标记状态、回写结果
- [ ] 策略建议有执行记录入口，间接用户能记录执行了什么
```

本节给清单，`acceptance-checklist.md` 加一句引用本文即可。

## 真实坑（预留，从真实间接用户使用中补）

- [ ] 间接用户看不懂 `actionType` 这类技术字段名（要显示 label，不显示 key）
- [ ] 间接用户不知道点哪导入（入口太隐蔽）
- [ ] 空数据时以为工具坏了（提示不到位）
- [ ] 规则调了不生效（没保存/没重新跑）
- [ ] 策略建议看了不知道怎么执行（没给操作步骤）
