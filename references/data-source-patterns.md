# 数据源接入模式（Data Source Patterns）

> **依赖与前置**
> - 前置：`domain-mapping.md`（识别数据里有哪些业务字段）
> - 被依赖：`cloud-sync-adapter.md`（数据库直连/API 拉取的接入实现）、`excel-import.md`（Excel 导入实现）
> - 可独立读。开工 3 问里"数据从哪来"答完后，用这篇定接入模式。

不同行业、不同场景的数据来源不同。开工前先明确"数据从哪来"，再选接入模式。**模式选错，后面全返工。**

## 四种接入模式

| 模式 | 适用场景 | 更新方式 | 典型技术 |
|------|---------|---------|---------|
| Excel/CSV 导入 | 数据由人整理成表格、不定期更新 | 手动上传/拖拽 | 前端解析（见 `excel-import.md`） |
| 数据库直连 | 已有 MySQL/PG，数据量大、要实时查询 | 后端接口查询 | Node + mysql2（见 `cloud-sync-adapter.md`） |
| API 拉取 | 数据在第三方系统/别的服务里 | 定时任务/按需拉取 | 后端 cron + fetch |
| 静态 JSON | 数据量小、只读展示、演示用 | 改代码重新部署 | 前端内嵌 `const RAW_DATA` |

## 选型决策树

```
数据从哪来？
│
├─ 人手工整理成表格？
│   └─ 是 → Excel/CSV 导入模式（解析 + 上传 + 快照）
│
├─ 已有数据库（MySQL/PG）？
│   └─ 是 → 数据库直连模式（后端接口查询，前端 fetch）
│
├─ 第三方系统有接口？
│   └─ 是 → API 拉取模式（后端拉取落库/缓存，前端只读）
│
└─ 一次性展示 / 数据量小 / 演示？
    └─ 是 → 静态 JSON 模式（最快跑通，后续可换）
```

## 各模式要点

### 1. Excel/CSV 导入
- 表头模糊匹配 + 清洗 + 交叉校验，详见 `excel-import.md`
- 数据落库后要留"解析摘要"（多少行、多少叶子实体、校验是否通过）给用户确认
- 更新流程：重新上传 → 覆盖写（事务 DELETE + INSERT）

### 2. 数据库直连
- 前端走 `CloudSync.callFunction`（fetch 版适配器），后端 `SELECT ... WHERE report_date = ?`
- **SQL 必须参数化**，防注入；连接池必用，防并发打满
- 快照表结构见 `cloud-deploy.md` 的 MySQL 建表模板
- 后端实现见 `cloud-sync-adapter.md` 的 MySQL 适配器

### 3. API 拉取
- 后端定时拉取（cron），存进快照表，前端只读快照——**前端不直接调第三方接口**
- 好处：第三方接口挂了不影响前端；限流/鉴权集中到后端一处
- 拉取失败要告警（写日志 + 状态字段），不能静默跳过

### 4. 静态 JSON
- 数据量小（几千行内）、只读、演示/汇报用
- 前端直接内嵌 `const RAW_DATA = [...]`，无网络依赖，`file://` 打开就能跑
- **最快的 MVP 方式**：V1 用静态 JSON 跑通流程，V2 需要多人共享时再换数据库模式

## 从静态 JSON 升级到数据库（渐进式）

```
V1: 静态 JSON（内嵌数据）→ 跑通看板逻辑
V2: 换 CloudSync 适配器 → 后端接数据库 → 前端业务代码零改动
```

接口契约不变（`callFunction(name, data)`），升级只改数据访问层，看板逻辑不动。这就是 `cloud-sync-adapter.md` 的核心价值。

## 判断要点

1. **数据更新频率**：每天更新 → 必须有上传/导入机制；每月更新 → 手动导入够用；实时 → 数据库直连
2. **数据量**：几万行内 → 前端解析够用；更大 → 后端聚合，前端只拿结果
3. **谁在维护数据**：业务人员 → 要上传入口；技术人员 → 后端脚本即可
4. **多人共享吗**：单机自用 → 静态/文件导入；多人看同一份 → 数据库 + 后端
